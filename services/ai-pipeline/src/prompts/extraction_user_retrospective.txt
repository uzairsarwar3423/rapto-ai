📋 RETROSPECTIVE EXTRACTION GUIDE — read before applying your task:

1. PAST vs. PRESENT. Most of a retro discusses the sprint that just ended.
   - "What slowed us down was the flaky CI" → HISTORICAL. Not a blocker.
     If the team expects it to recur, it is a RISK (category QUALITY/TECHNICAL).
   - "CI is still flaky and blocking merges right now" → ACTIVE BLOCKER.

2. DECISIONS = AGREED PROCESS CHANGES. These are the most important output of
   a retro. "Let's try pairing on all migrations next sprint — everyone ok?
   — Yes." is a PROCESS decision (reversible: true — it is an experiment).
   A suggestion nobody agreed to is NOT a decision.

3. ACTION ITEMS = IMPROVEMENTS WITH AN OWNER. "Omar will set up the flaky-test
   dashboard before next retro" is an action item. "We should write more tests"
   with no owner is NOT.

4. COMMITMENTS. First-person promises made in the retro ("I'll write up the
   on-call runbook") are commitments as usual.

5. VENTING IS NOT DATA. Complaints and kudos are summary context only — do not
   turn them into blockers, risks or decisions.

GROUNDING RULES:
Each transcript line is "Speaker Name: what they said". Report only what the
transcript supports — never fill a field to make an item look complete. Unknown
owner, deadline or decision-maker → null. Every item needs an evidence_quote copied
verbatim from the transcript; an item you cannot quote is not extracted.

SPEAKER MATCHING RULE:
Transcript speakers may use shortened names (e.g., "Ahmed" = "Ahmed Hassan",
"Sara" = "Sara Khan"). Match a spoken name to the participant list by first
name unless two participants share a first name — then use surname or
contextual clues to disambiguate. If still ambiguous, use the name exactly as
spoken in the transcript. Never invent a person who is not in the transcript.
